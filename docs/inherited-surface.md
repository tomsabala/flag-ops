# Inherited surface — keep / park / delete

Written by hand in `ROADMAP.md` P0, 2026-10-29. This is the one document in
`docs/` that is **not** generated by a check harness: it is a decision record,
not a measurement, and every row names the evidence its decision rests on.

`flag-ops` is a copy of a single-robot ROS 2 Humble + Gazebo Harmonic
navigation lab. P0 decides the fate of every inherited subsystem *before*
anything is built on top of it, so that no later phase inherits a surface

### Correction: the car's `JointStatePublisher` is load-bearing

P0 deleted the plugin from both models on the strength of an audit line, then
measured what happened. It is the one place in this phase where the plan was
wrong and the measurement decided.

**Mechanism, READ from `/opt/gz_ws/src/ardupilot_gazebo/src/ArduPilotPlugin.cc:1355-1380`:**
all four of `ral_car`'s `<control>` blocks set `<useForce>1</useForce>`. In that
branch the plugin *reads* `components::JointVelocity` for a `VELOCITY` control
and `components::JointPosition` for a `POSITION` one, and **never creates
them** — when the component is absent it silently skips the PID update and
leaves `JointForceCmd` at its previous value. `gz::sim::systems::Physics` only
*updates* those components. `JointStatePublisher` is what creates them. So
deleting the plugin removed the autopilot's steering and throttle **feedback**
while leaving every command path intact: a silent open loop.

**MEASURED 2026-10-29**, `baseline_car` through `scripts/checks/car_nav_check.sh`,
nothing else changed between the two runs:

| | with the plugin | without it |
| --- | --- | --- |
| verdict | **13/13** | checks **7, 8, 10 FAIL** |
| mission | terminal at 5.8 s sim | no terminal condition in 180 s sim |
| final truth vs goal (6.500, 4.000) | (5.552, 3.889), 0.954 m | (3.700, 3.324), 2.880 m |
| contacts | 0 raw `/bumper` reports | 88,228 raw reports against `wall_a_lower` |
| measured minimum turning radius | 59.051 m — never near full lock | 0.525 m — pinned near the 0.611 m geometric limit for the whole run |

The plugin is therefore **kept on `ral_car` and deleted on `ral_roomba`**, with
the reason recorded in the model file itself so the next reader cannot repeat
the deletion. The `/joint_states` **bridge row** is a different artifact — a
ROS topic, not a gz component — and stays deleted for both robots, which is why
the car still loses its six revolute TF frames while its control loop works.

This is also the reason the triage runs the proof harness for a *parked*
platform at all: without `car_nav_check.sh`, a deletion justified by "nothing
reads it" would have shipped as a silently broken autopilot.

## 3. Parked: the car / ArduRover / MAVROS stack

**Owner decision, 2026-10-29 (`ROADMAP.md` §7.1): park, do not delete.** The
stack stays buildable, tested and evidenced, and out of the CTF match path. No
ArduRover SITL process runs inside a match.

`scripts/checks/car_nav_check.sh` returning **13/13** is the measurement that
proves the park is intact. Every phase re-runs it.

## 5. What P0 did **not** change

P0's constraint is **zero behaviour change beyond the deletions above**. The
map, the world geometry, the plant limits, the Nav2 tuning, the AMCL
configuration, the fault mechanisms and the metric definitions are all
untouched.

`baseline_roomba` is the regression anchor for every later phase, and the
acceptance test was its recorded three-run spread: `mission_duration_s`
37.480–38.058 s, `path_length_m` 13.486–13.537 m.

**MEASURED 2026-10-29**, three runs on this branch and — because one endpoint
fell outside the recorded band — three contemporaneous control runs on
unmodified `main`, on the same host, with no other `ral:*` container running:

| Source | `mission_duration_s` | spread | `path_length_m` |
| --- | --- | --- | --- |
| recorded band (2026-10-25, the acceptance test) | 37.480 – 38.058 | 1.5 % | 13.486 – 13.537 |
| this branch, 3 runs | **37.384 – 37.950** | 1.5 % | **13.496 – 13.518** |
| `main`, 3 control runs, same day | 37.240 – 38.296 | 2.8 % | 13.498 – 13.510 |

This branch's minimum is 0.096 s (0.26 %) below the recorded minimum, so the
acceptance test as written did not pass on its first reading. The control run
is what settles it: **this branch's whole range lies strictly inside the range
the unmodified code produces today** (37.240 – 38.296 s), and the branch spread
is *narrower* than the control's. The excursion is run-to-run nondeterminism,
not a P0 effect — `nav2_amcl` exposes no seed and ROS callback scheduling is
not deterministic, which `docs/repeatability-baseline_roomba.md` says in its
own words.

Recording the control rather than widening the band is deliberate: a band
adjusted to fit a measurement stops being a test.

All three mission outcomes on this branch were `nav2:STATUS_SUCCEEDED` with
`number_of_recoveries = 0`, matching the recorded runs.
